# 截断标记误报修复与验证

已完成回归测试、规则修复、两策略全量重跑与前后影响核对。当前结果位于`outputs/balanced/`、`outputs/conservative/`和`outputs/comparison/`。原始数据保持不变；本次未将另外4条人工确认的暂缓结论自动写入准入规则。

## 问题、备选方案与实现

初版只要工具返回含`[TRUNCATED]`或`...TRUNCATED`就以RECORDED_TRUNCATION暂缓。真实轨迹`7bce5aa6ee3bc6fa68957d61`、原始表解压第53行`/steps/27/result`中，该文本是测试断言：

```text
208    expect(((deep.l1 as Nested).l2.l3.l4.l5 as { l6: unknown }).l6).toBe('[TRUNCATED]');
```

这是合法代码常量，不能证明记录被截断。初版的“原始结果已被截断”措辞也过于肯定。

备选方案与决策：

| 方案 | 取舍 |
| --- | --- |
| 完全关闭标记检查 | 放弃；会失去本批68处独立截断提示 |
| 所有引号中的标记都忽略 | 放弃；JSON或日志引号也可能包住实际截断提示 |
| 所有read/grep输出都忽略 | 放弃；真实截断提示也出现在读取代码的返回中 |
| 按语境区分每个标记，未知仍暂缓 | 采用；既修复可证实的误报，又保留未能解释的疑问 |

实现位于`agent_qc/rules.py`的`truncation_contexts`：识别独立提示、源码字面量与未知语境。只有位于完整引号内、且该行具有源码行号或赋值/断言等明确代码特征的标记，才记录非阻断TRUNCATION_LITERAL。识别逐个标记进行，一处常量不会掩盖同一行的另一个提示。纯JSON、单独带引号的标记、未闭合引号及普通文本中的标记，仍以证据不足暂缓。

RECORDED_TRUNCATION现在表示“存在截断提示或语境不明的标记，关键反馈是否缺失待核验”，不声称已证明任务错误。证据包含原结果中的字符偏移、结果文本行号、列号、语境类型和附近原文；JSONL源行及步骤Pointer仍保留。

该实现是词法启发式，不是全语言解析器，也无法发现所有无标记截断；这些限制已写入每次运行的summary。即使独立成行的标记也不等于已证明缺失部分影响训练，因此归入“证据不足→暂缓”，而不是“明确损坏→排除”。

## 三类问题的区分

| 类别 | 判据 | 例子与处置 |
| --- | --- | --- |
| 数据本身存在问题 | 可直接证实训练表示违反契约 | 无效JSON、孤立返回：按明确缺陷阻断/排除；不把正常执行失败当损坏 |
| 当前证据不足 | 记录可能合法，但现有证据无法核实是否可消费 | 真正的截断提示、未知标记语境、重建schema冲突：暂缓并记录所缺证据；预算外继续暂缓 |
| 合法但不符合训练目标 | 表示可用，却不满足预先声明的筛选目标 | 零工具调用：NO_TOOL_TARGET按目标排除，不能算数据错误 |

本例的代码常量属于合法内容，不能仅因文本标记归入证据不足；但整轨迹仍有独立schema疑问。保留失败/重试与信任最终答案是不同问题，本修复没有增加任务成功保证。
